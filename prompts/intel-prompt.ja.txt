決めるのを手伝う。公開用のレポートを書くのではない。

リポジトリ: https://github.com/yomiplush/2026-world-is-a-fuck-incident

進め方:

1. 次の順に読む: README_jp.md、docs/07-oracle-java-oct2026.ja.md、
   docs/08-intel-sources.ja.md、SOURCES.ja.md。
   CVE ID、CVSS、影響版、修正版の根拠は、この4ファイルだけにすること。記憶から CVE を
   足さない。もっともらしい版番号を補わない。他の勧告から思い出した項目を混ぜない。

2. 答える前にデータを更新し、差分を見せる:

     git clone https://github.com/yomiplush/2026-world-is-a-fuck-incident.git
     cd 2026-world-is-a-fuck-incident
     tools/intel/fetch-intel

   出力と、docs/07 §1 / docs/08 §3 の数値を比べる。動いていた場合（KEV の追加、新しい
   Oracle のリリース、MSRC の件数変化など）は、回答の冒頭で1文で述べ、**新しい方を
   根拠にする**（文書ではない）。取得に失敗したら、どのソースが失敗したかを述べ、
   日付付きスナップショットで続行し、「スナップショット基準」と明記する。

3. 次の2つを毎回分ける。同じ列ではない:
     - その脆弱性の影響を**受ける**版（例: Oracle の表の 21.0.12.1）
     - 修正を**含む**版（例: 21.0.13）
   ベンダの「影響版」一覧を修正版として報告しないこと。ベンダの修正ビルドが未提供・
   遅延している場合（サードパーティの OpenJDK ビルドは Oracle より遅れる）は、丸めずに
   そう書く。

4. そのうえで、私の環境だけを扱う。まず読み取り専用で、生の出力を見せる:

     java -version
     for j in $(command -v java javac 2>/dev/null) /usr/lib/jvm/*/bin/java; do
       [ -x "$j" ] && printf '%s -> ' "$j" && "$j" -version 2>&1 | head -1
     done
     docker ps -q | xargs -r -I{} sh -c 'docker exec {} java -version 2>&1 | head -1 | sed "s|^|{} |"'

   見るのは**ビルド文字列**（21.0.13+10）で、製品名ではない。ホストやコンテナを
   確認できない場合は、その対象を「判断できない」と書く。仮定しない。

5. 回答は次の4リスト固定。各項目に出所と取得日を付ける:

     A. 私の環境で確定したもの（観測した版文字列付き）
     B. 今すぐ対応が必要（なぜ今か: KEV 収載 / インターネット公開 / 修正が無い）
     C. 判断できない（および決着させるコマンド1つ）
     D. 対象外（そう判断した観測）

   そのあとに「この答えが変わる条件」——違っていたら項目がリスト間を移動する事実を
   2〜3個。

守ること:
- 部分的な緩和を「修正」と呼ばない。回避策が1つの経路を塞ぐだけなら「部分的」と書く。
- 「CISA KEV に無い」は「悪用が未確認」の意味で、安全の意味ではない。この2文を混ぜない。
- 情報源が停止・メンテナンス中だった場合は、その名前と、代わりに使ったものを書く。
- 状態を変える操作（パッケージ導入、イメージ pull、再起動）は、正確なコマンドを示して
  私の承認を待つ。承認は計画単位ではなくコマンド単位。
- 私の環境（送信前に埋める）:
    OS / パッチ手段: <例: Arch Linux, pacman / Ubuntu 24.04, apt / RHEL 9, dnf>
    公開状況:        <インターネット公開のホスト、不明なら「不明」>
    ランタイム:      <把握している Java の版、不明なら「不明」>
    コンテナ:        <docker/podman の有無、グループ権限の有無>
    アクセス:        <触れてよい ssh 先、または「ローカルのみ」>
