リポジトリ: https://github.com/yomiplush/2026-world-is-a-fuck-incident

次の順で進めてください。

1. README_jp.md を読み、続けて docs/01-php2shell.ja.md、docs/02-nodejs-oct2026.ja.md、
   docs/07-oracle-java-oct2026.ja.md、docs/09-gitlab-19-5-1.ja.md、
   docs/10-litellm-1-107-0.ja.md を読む。
   バージョンの対応表と緩和策は、この5つのファイルだけを根拠にすること。
   記憶から CVE や影響バージョンを補わない。

2. まず読み取り専用で実行し、生の出力をそのまま見せること:
     tools/php2shell/bin/p2s-audit --json
     tools/node/nodefix-audit
     java -version
   --target <ssh-host> は、私が名前を挙げたホストにだけ付ける。Java は、見つけられる
   すべての JVM について**ビルド文字列**（例: 21.0.13+10）を読む。ホストとコンテナの両方。
   コマンドは docs/07 §6 にある。

3. README_jp.md の「2-3. 判定」の表のとおりに分岐する。
   出力がどの行にも当てはまらない場合は、推測せず止まって報告する。

   Java については、注意喚起が「影響を受ける」としている版と、修正を**含む**版を
   必ず分ける（docs/07 §2）。Oracle の "Supported Versions Affected" は修正版の一覧では
   ない。私の使っているベンダの修正ビルドがまだ無い場合は、Oracle の版に丸めず、
   そう書くこと。

   GitLab と LiteLLM は PHP / Node / Java と性質が違う。GitLab は「版を上げる」で直るが、
   LiteLLM は「ファイルを消して資格情報をローテートする」までが1組。1.107.0 を
   アンインストールしたことを対処の完了と呼ばないこと。cook.pth が残っている可能性のある
   環境で pip を実行しないこと（docs/10 §4）。

4. 変更の前に、必ず --dry-run で実行して計画を見せること。私の承認を待つ。
   複数ステップをまとめて承認扱いにしない。

5. 変更のたびに README_jp.md の「2-5. 検証」で確認する。コンテナ再起動を跨ぐ確認も含める。
   バージョン文字列だけで成功と判断しない。

6. 最後に次を報告する:
   - 見つかったもの（実行中のバイナリから読んだバージョン付き）
   - 変更したもの（使ったコマンド付き）
   - できなかったこと、その理由
   - 残っている作業
   部分的な緩和を「修正」と表現しないこと。
