[English](13-recent-criticals.md) | [**日本語**](13-recent-criticals.ja.md)

> **2026-10-23 07:25 JST に再取得。** 同じクエリを10時間後に流すと **125件**が返ります
> （11件入り、10件出た）。NVD が PHP の2件のうち1件を再評価し、深刻度フィルタが CNA の
> スコアだけを持つ行を数えないためです。数字の再計算の過程で、収集ツールが CNA のスコアを
> 採用していた不具合も見つかりました。§2 は 2026-10-22 時点の測定として残し、**§9** に
> 何が変わり、なぜ変わったか（修正後の ≥9.8 件数を含む）を書きます。

「他に深刻なものは無いの？」は正しい問いですが、形が良くありません。NVD を2週間分なめると
**CRITICAL が120件**返り、上から順に読むと、自分が持っていないルータに1日を使い、
悪用されている1件については何も分からないまま終わります。

そこでこの文書は「走査」＋「フィルタ」です。データが何を言っているか、何が残ったか、そして
数字を額面どおり受け取ると誤る**4つの罠**。

## 5. データの4つの罠

### 5.1 同じ CVE に CVSS が2つあり、高い方が自分に当てはまるとは限らない

MOVEit と TeamCity は、1つのレコードに **CNA の 8.1** と **NVD の 9.8** が併記されています。
差は1つの要素です。

```
8.1  CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:H    ← CNA（Progress / JetBrains）
9.8  CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H    ← NVD
```

`AC:H` は「攻撃者が制御できない条件が要る」の意味で、前提を知っているベンダは「難しい」と
言っています。`AC:L` は「易しい」。最大値をトリアージに使うと、**他人の仮定**を読むことになります。
**数字ではなく、ベクターと出所を引用してください。**

### 5.2 CVSS 3.1 と 4.0 は丸め誤差以上に食い違う

PHP は **CVSS 3.1 で 9.8**、**CVSS 4.0 で 9.2**。このリポジトリが 9.2 を使うのは PHP 自身の
勧告がそうだからです。どちらも正しく、攻撃複雑度の仮定が違う別の尺度です。ラベル無しで混ぜた
表は、何とも比較できません。

### 5.3 EPSS は「数日前の CVE」には使えない

期間内の最高 EPSS は **3.0%**。KEV 収載の2件はこうです。

| CVE | EPSS | KEV |
|---|--:|---|
| `CVE-2026-102764`（BeyondTrust） | 1.2% | KEV 収載、**期限は既に経過** |
| `CVE-2026-96656`（Plex） | 0.76% | KEV 収載、期限 2026-10-23 |

EPSS は「これまでに蓄積した証拠を踏まえた悪用確率」なので、先週公開された CVE には証拠が
ほとんどありません。同じ週の判断では **KEV と露出が EPSS に勝ち**、「EPSS が低い」は待つ理由に
なりません。EPSS は6〜18か月の裾に使うものです。

### 5.4 件数はリスクではなく「開示のまとめ方」を測っている

- 120件中34件は Oracle の四半期 CPU——1回の公開イベント。
- 38件はコンシューマ IoT のファームウェア。スキャン型 CNA 由来が多く、全部 9.8〜10.0、
  所有者にパッチが提供されないものも多い。
- 18件は IBM の一括公開。
- NVD が CPE を紐付けているのは **120件中32件（27%）**。NVD だけでベンダ別集計をすると、
  3分の1しか見えません。

「今週、重大な脆弱性が40%増えました」という週報は、**プレスリリースを数えている**だけです。

## 6. この走査が支えるトリアージ手順

1. **動かしていない行を捨てる。** Oracle EBS、Fabric OS、DataStage——棚卸しに無ければ終わり。
   （これで120件の60%が消えます。）
2. **残りは最大スコアではなく CNA のベクターを読む。** `AC:H` と `PR:H` が優先度を変えます。
   社内ネットワークで管理者認証が要る 10.0 は、保守作業です。
3. **EPSS より先に KEV を見る。** KEV は期限付きの「悪用観測」の主張、EPSS は遅れのある確率。
4. **「どれくらい悪いか」より「何を持っているか」を問う。** CI サーバ（TeamCity）と MFT
   （MOVEit）は全システムの資格情報を持ち、メディアサーバ（Plex）はアカウントのトークンを
   持ちます。この問いの方が、どのスコアより速く順番を入れ替えます。
5. **やらないと決めたことと理由を書く。** 次の走査では同じ CVE に新しい数字が付いて再登場し、
   あなたは理由を覚えていません。

### 9.1 5つ目の罠: 深刻度フィルタは NVD 自身の評価しか数えない

`cvssV3Severity=CRITICAL` は **Primary** の指標で答えます。`Awaiting Analysis` のまま
CNA（Secondary）のスコアしか持たないレコードは、値がいくつでも対象外です。

```bash
curl -s 'https://services.nvd.nist.gov/rest/json/cves/2.0?cveId=CVE-2026-101809&cvssV3Severity=CRITICAL' | jq .totalResults
# → 0    （レコードの指標は secalert_us@oracle.com の Secondary 10.0 のみ）
```

2回の取得の間に抜けた10件のうち9件がこの状態です（`Awaiting Analysis` / `Undergoing Analysis` /
`Deferred`）。残る1件は §9.2 の再評価です。つまり「CRITICAL が N 件」は「**解析済み**のレコードが N 件」であって、
「危険な脆弱性が N 件」ではありません。§5.1 と同種の誤りを1層下でやっていることになります。
「どのスコアを読むか」ではなく、**「クエリがどのスコアを見ているか」**。

### 9.2 NVD が PHP の2件のうち1件を再評価した

`CVE-2026-109619` は 2026-10-22 21:17Z に 9.8 → **8.1**（`AC:L` → `AC:H`）。
`CVE-2026-109618` は 9.8 のまま。PHP 自身の CVSS 4.0（両方 9.2）と修正内容は変わりません。
実務上の影響は狭いが知っておく価値があります。「9.0 以上だけ見る」トリアージでは、
**同じアドバイザリの2件のうち片方だけが消える**。スコアではなくアドバイザリ単位で適用する。

### 9.3 収集ツールが誤った指標を読んでいた

`collect_nvd_critical` は `metrics.cvssMetricV31[0]` をスコアとして採用していました。NVD は
一部のレコードで CNA の指標を NVD のものより先に並べ、両者は深刻度帯ごと食い違います。
`CVE-2026-95695` は Secondary 7.4（IBM）と Primary 9.1（NVD）を同時に持ち、CRITICAL
フィルタで選ばれた行が 7.4 として記録されていました。ツールは `type: Primary` を優先し、
無い場合に他の値へフォールバックするよう修正しました。**同じ125行**で 9.8 以上は 53 → **72**、
ちょうど 10.0 は 13 のままです。

これは世界の変化ではなく**計器の欠陥**であり、§2 を「その時点の測定」として読む理由です。
古い `data/` スナップショットは取得時のまま残します。

### 9.4 窓の最高 EPSS は php2shell になった

`CVE-2026-109619` が 5.76%（パーセンタイル 0.930）、`CVE-2026-109618` が 5.31%（0.926）。
いずれも 2026-10-22 付です。§5.3 は「最大 3.0%」「EPSS は1週間前の CVE にはほぼ無力」と
書きました。前半はもう古く、後半は正しいままです。5.3% は絶対値としては低い。ただし窓の
最高値であり、公開 PoC があり、CISA は今も「観測していない」と記録している。この2つが別の
主張である理由は [`docs/08` §4](08-intel-sources.ja.md) にあります。
