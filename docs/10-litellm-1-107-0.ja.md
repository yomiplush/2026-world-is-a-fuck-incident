# LiteLLM 1.107.0 — サプライチェーン侵害（資格情報窃取＋遠隔ローダ）

[English](10-litellm-1-107-0.md) | [**日本語**](10-litellm-1-107-0.ja.md)

このバッチで唯一、**「間違った版を入れたこと自体が侵害」**になる事案です。LLM ゲートウェイである
`litellm` は多数のプロバイダの API キーをまとめて保持します。その 1.107.0 の wheel は
**Python が起動するたびに実行**され、資格情報を盗み、毎時コードを取りに行くローダを残します。

**7か月で2回目**。2026年3月にも同じ `.pth` の手口で侵害されています。

## 1. 何が起きたか

| 項目 | 値 |
|---|---|
| パッケージ | `litellm`（PyPI）＋ Docker イメージ |
| 問題の版 | **1.107.0** — wheel 7種、加えて `pyproject.toml` を改ざんされた sdist |
| 手口 | `.pth` と `sitecustomize.py` が **Python 起動のたびに**自動実行される |
| ペイロード | 資格情報窃取（`privcollect`）＋ GitHub のデッドドロップを毎時確認し、攻撃者の Python を実行する常駐デーモン |
| ビルド元 | **そっくりリポジトリ** `Berri-AI/litellm`（本物は `BerriAI/litellm`）— 現在は 404 |
| PyPI の現状 | 1.107.0 は**削除済み**。公開されている最新は **1.106.2** |
| Docker の現状 | `latest` / `main-latest` / `main-stable` は悪性ビルドを指さないよう差し替え（事案 issue の 2026-10-21 17:13 UTC 時点） |
| GHSA | 2026-10-22 時点で**未公開**。CVE の形をした事案ではない |
| 前例 | **2026年3月24日**: `litellm` 1.82.7 / 1.82.8、悪性 `litellm_init.pth`、同じ自動実行 |

2026-10-22 に PyPI の JSON API で確認: `/pypi/litellm/json` の最新は `1.106.2`、`1.107.0` の
ファイル数は **0**。隔離が起きたことを確認する最短のコマンドです。

```bash
curl -s https://pypi.org/pypi/litellm/json | jq -r '.info.version, (.releases["1.107.0"]|length)'
# 1.106.2
# 0
```

## 2. なぜ「よくある不良パッケージ」より厄介か

3つが重なります。

1. **import されなくても動く。** `cook.pth` はインタプリタ起動時に実行され（`.pth` の行が
   `import` で始まると実行される）、`sitecustomize.py` を読み込みます。そのパッケージが入った
   環境で Python を起動するだけで発火します。**`pip` 自身も Python** です。
2. **LiteLLM は資格情報の集積点。** 設計上、OpenAI / Anthropic / Gemini / Azure などの
   プロバイダキー、DB の URL、マスターキーを保持します。窃取側は権限昇格をする必要がなく、
   秘密はすでに手の届く場所にあります。
3. **ローダを残す。** 第2段は wheel の外に常駐し、GitHub のデッドドロップを見続けます。
   「パッケージを消した」＝「ホストがきれい」ではありません。

wheel 内のファイル（`litellm-1.107.0.data/purelib/`、site-packages 直下に展開される）:

| ファイル | サイズ | 意味 |
|---|--:|---|
| `cook.pth` | 12 B | 引き金。インタプリタ起動ごとに実行される |
| `cook.py` | 22,252 B | 第1段: 窃取＋第2段の設置 |
| `sitecustomize.py` | 25,509 B | 第2段: 起動時に、あなたのコードより先に走る |

## 3. 自分は該当するか

```bash
# 1) パッケージの有無と版
python3 -c "import litellm, sys; print(litellm.__version__, sys.prefix)" 2>/dev/null \
  || pip show litellm 2>/dev/null | head -2

# 2) site-packages にペイロードのファイルが残っていないか
python3 - <<'PY'
import site, pathlib
for d in set(site.getsitepackages() + [site.getusersitepackages()]):
    for name in ("cook.pth", "cook.py", "sitecustomize.py"):
        p = pathlib.Path(d) / name
        if p.exists():
            print(f"HIT {p}  {p.stat().st_size} bytes")
PY

# 3) 第2段の痕跡（事案の一次記録に記載）
ls -la /tmp/.pc_sq_* /tmp/.pc_e_* /tmp/remote_code_loader.lock 2>/dev/null
ps -eo pid,ppid,cwd,args 2>/dev/null | awk '$3=="/" && /python/'

# 4) 実際に動いているイメージのダイジェスト
docker ps -q | xargs -r docker inspect --format '{{.Name}} {{.Config.Image}} {{.Image}}'
docker images --digests | grep -i litellm
```

(2) と (3) が**陰性でも潔白の証明にはなりません**。コンテナや `/tmp` のクリーンアップで
痕跡は消えます。言えるのは「痕跡が見つからない」であって「侵害されていない」ではありません。

## 4. 対処（順番に意味がある）

順番は体裁の問題ではありません。**先に `pip` を走らせると、その環境でペイロードが再実行されます。**

1. **シェルから**、`cook.pth` / `cook.py` / `sitecustomize.py` と、対応する
   `__pycache__/cook*.pyc` / `sitecustomize*.pyc` を**すべての**該当 site-packages から削除する。
2. **常駐デーモンを殺す**（`/tmp/remote_code_loader.lock` を保持している）。
3. **版を固定して入れ直す**: `pip install 'litellm==1.106.2'`。venv やイメージは、
   掃除するより**作り直す方が確実**です。
4. **外部送信は成立したと仮定する。** 1.107.0 を外向き通信のあるホストに入れたことがあるなら
   そう扱う。マーカーファイルがあれば確定、無くても何の証明にもなりません。
5. **到達可能だったものを全部ローテート**: インスタンス／タスクの IAM ロール、LiteLLM の
   DB に入っている全プロバイダキー、マスターキーと仮想キー、`DATABASE_URL` のパスワード、
   そのホスト上のプロセスの環境にあった秘密すべて。
6. **クラウドの監査ログ**で、導入時刻前後のインスタンスロールによる `GetCallerIdentity` と、
   その後その資格情報が自インフラ外から使われていないかを確認する。

一次記録が「クリーン」としている版: `1.103.6` / `1.103.7` / `1.104.4` / `1.104.5` / `1.105.2` /
`1.105.3` / `1.106.0` / `1.106.1` / `1.106.2` / `1.107.0rc1` / `1.107.0rc2`、
`litellm-proxy-extras` 0.4.108〜0.4.110、記載の `litellm-enterprise`。**Docker イメージは
検査されていない**と明記されているので、1.107.0 を指したことのあるダイジェストは疑ってください。

## 5. どう入り込んだか（そしてなぜ再発するか）

2つの機序。1つは検証済み、1つは報道ベースです。

- **検証済み**: wheel のビルド来歴が、本物 `BerriAI/litellm` ではなく**そっくりリポジトリ
  `Berri-AI/litellm`** を指している。リリースワークフローが信頼すべきでない供給元を信頼した。
  そのリポジトリは現在 404。
- **ベンダ発言（The Hacker News 経由＝二次）**: 3人のエンジニアの GitHub アカウントが、
  **GitHub CLI の OAuth トークン窃取**を経由して使われた。1つが `project-releaser` を起動し、
  もう1つが承認した。関与したトークンは失効、組織は1ユーザーに縮小。

行動を変えるべきは3月の前例です。`1.82.7` / `1.82.8` は**git タグもリリースも無いまま PyPI に
直接**アップロードされ、同じ `.pth` 自動実行を使っていました。7か月で2回ということは、
問題は資格情報だけでなく**手順**にあります。

## 6. 一段落でまとめると

読んでいない依存は「自分が実行しているコード」で、`.pth` は「インストール」を「実行」に変えます。
効いたはずの対策は安い: ハッシュ付きで版を固定する、ロックファイルを持つ、スキャナに
「リリースと git タグの差分」を見せる、リリースワークフローを正規リポジトリ以外から
ビルドさせない。**AI ゲートウェイを運用しているなら、それは資格情報の金庫**として扱い、
イメージダイジェストを秘密と同程度に扱ってください。
