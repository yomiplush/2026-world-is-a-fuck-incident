# LiteLLM 1.107.0 — supply-chain compromise (credential stealer + remote loader)

[English](10-litellm-1-107-0.md) | [**日本語**](10-litellm-1-107-0.ja.md)

The one incident in this batch where **installing the wrong version is the compromise**. The
`litellm` package — an LLM gateway that holds API keys for many providers at once — shipped a
release whose wheels execute on any Python start, steal credentials, and leave a loader behind
that fetches more code every hour.

Second time in seven months: the same package was compromised in March 2026 with the same
`.pth` trick.

## 1. What happened

| Field | Value |
|---|---|
| Package | `litellm` (PyPI), plus Docker images |
| Bad version | **1.107.0** — 7 wheels, plus an sdist with a tampered `pyproject.toml` |
| Technique | `.pth` file + `sitecustomize.py` auto-executed on **every** Python start |
| Payload | credential stealer (`privcollect`) + background daemon that polls a GitHub dead drop hourly and runs attacker-supplied Python |
| Built from | a **lookalike repository** `Berri-AI/litellm` (real project: `BerriAI/litellm`) — now 404 |
| Current PyPI state | 1.107.0 **removed**; latest published version is **1.106.2** |
| Docker state | `latest`, `main-latest`, `main-stable` re-pointed away from the malicious build (per the incident issue, 2026-10-21 17:13 UTC) |
| GHSA | **none published** as of 2026-10-22 — this is not a CVE-shaped incident |
| Precedent | **March 24, 2026**: `litellm` 1.82.7 / 1.82.8, malicious `litellm_init.pth`, same auto-execution |

Verified against the PyPI JSON API on 2026-10-22: `/pypi/litellm/json` reports `1.106.2` as the
latest release and `1.107.0` with **zero files**. That is the cleanest single check that the
quarantine happened, and it is a one-liner:

```bash
curl -s https://pypi.org/pypi/litellm/json | jq -r '.info.version, (.releases["1.107.0"]|length)'
# 1.106.2
# 0
```

## 2. Why this one is worse than a normal bad package

Three things compound:

1. **It runs without being imported.** `cook.pth` is executed by the interpreter at startup
   (a `.pth` file whose line starts with `import` is executed), and it loads
   `sitecustomize.py`. Merely starting Python in an environment that has the package installed
   is enough — including `pip`, which is itself Python.
2. **A LiteLLM install is a credential concentrate.** By design it holds provider keys for
   OpenAI, Anthropic, Gemini, Azure and others, plus a database URL and a master key. A
   stealer that lands there does not need to escalate; the secrets are already in reach.
3. **It leaves a loader.** The second stage lives outside the wheel and keeps checking a
   GitHub dead drop, so "the package is gone" does not mean "the host is clean".

The wheel artefacts, in `litellm-1.107.0.data/purelib/` (installed into the site-packages
root):

| File | Size | Why it matters |
|---|--:|---|
| `cook.pth` | 12 B | the trigger: executed by every interpreter start |
| `cook.py` | 22,252 B | stage 1: stealer + installer of stage 2 |
| `sitecustomize.py` | 25,509 B | stage 2 hook: runs at interpreter startup, before your code |

## 3. Am I affected?

```bash
# 1) Is the package present, and at what version?
python3 -c "import litellm, sys; print(litellm.__version__, sys.prefix)" 2>/dev/null \
  || pip show litellm 2>/dev/null | head -2

# 2) Do the payload files exist in any site-packages?
python3 - <<'PY'
import site, pathlib
for d in set(site.getsitepackages() + [site.getusersitepackages()]):
    for name in ("cook.pth", "cook.py", "sitecustomize.py"):
        p = pathlib.Path(d) / name
        if p.exists():
            print(f"HIT {p}  {p.stat().st_size} bytes")
PY

# 3) Second-stage traces (from the incident write-up)
ls -la /tmp/.pc_sq_* /tmp/.pc_e_* /tmp/remote_code_loader.lock 2>/dev/null
ps -eo pid,ppid,cwd,args 2>/dev/null | awk '$3=="/" && /python/'

# 4) Docker images: what digest is actually deployed?
docker ps -q | xargs -r docker inspect --format '{{.Name}} {{.Config.Image}} {{.Image}}'
docker images --digests | grep -i litellm
```

A **negative** result on (2) and (3) is not proof of innocence — containers and `/tmp` cleanup
remove the markers. The honest statement is "no artefact found", not "not compromised".

## 4. Remediation, in the order that matters

The order is not cosmetic: **running `pip` first re-executes the payload** in that environment.

1. **From a shell, delete** `cook.pth`, `cook.py`, `sitecustomize.py` and any matching
   `__pycache__/cook*.pyc` / `sitecustomize*.pyc` from **every** affected site-packages.
2. **Kill the detached daemon** (it holds `/tmp/remote_code_loader.lock`).
3. **Reinstall pinned**: `pip install 'litellm==1.106.2'`. Rebuilding the venv or image from
   scratch is better than cleaning it.
4. **Assume exfiltration** if 1.107.0 was ever installed on a host with outbound internet. The
   marker file proves success; its absence proves nothing.
5. **Rotate everything that host could reach**: the instance/task IAM role, every provider key
   stored in the LiteLLM proxy DB, the master and virtual keys, the `DATABASE_URL` password,
   and any secret that was in the environment of any process there.
6. **Check the cloud audit log** for `GetCallerIdentity` from the instance role around install
   time, then for use of those credentials from outside your infrastructure.

Known-clean versions per the incident write-up: `1.103.6`, `1.103.7`, `1.104.4`, `1.104.5`,
`1.105.2`, `1.105.3`, `1.106.0`, `1.106.1`, `1.106.2`, `1.107.0rc1`, `1.107.0rc2`, plus
`litellm-proxy-extras` 0.4.108–0.4.110 and the listed `litellm-enterprise` builds. The
write-up explicitly says the Docker images were **not** inspected — treat any registry digest
that ever resolved to 1.107.0 as suspect.

## 5. How it got in (and why it will happen again)

Two mechanisms, one verified and one reported:

- **Verified**: the wheel's build provenance points at a lookalike repository,
  `Berri-AI/litellm`, instead of `BerriAI/litellm`. The project's release workflow trusted a
  source it should not have. The lookalike repository is now gone (404).
- **Reported by the vendor** (via The Hacker News, i.e. secondary): three engineers' GitHub
  accounts were used via stolen **GitHub CLI OAuth tokens**; one account triggered the
  `project-releaser` run and another approved it. All involved tokens were revoked and the
  organisation was reduced to one user.

The March incident is the part that should change behaviour: `1.82.7`/`1.82.8` were uploaded
**straight to PyPI with no corresponding git tag or release**, using the same `.pth`
auto-execution. Two compromises of the same package in seven months means the *process*, not
just the credential, is the problem.

## 6. What this teaches, in one paragraph

A dependency you did not read is code you are running, and a `.pth` file turns "installed" into
"executed". The controls that would have caught this are cheap: pin exact versions with
hashes, keep a lockfile, let a scanner see the diff between a release and its git tag, and
never let a release workflow build from anything but the canonical repository. If you operate
an AI gateway, assume it is a credential vault and treat its image digests like secrets.
