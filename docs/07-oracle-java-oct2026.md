# Oracle Java SE — October 2026 Critical Patch Update

[English](07-oracle-java-oct2026.md) | [**日本語**](07-oracle-java-oct2026.ja.md)

Oracle's October 2026 Critical Patch Update (CPU) carries **55 Java SE security patches**.
This document records what those 55 are, which builds contain the fixes, and how to tell
whether a given host is affected — with every number traceable to
[`data/2026-10-22/oracle-java-oct2026.json`](../data/2026-10-22/oracle-java-oct2026.json),
which is regenerated by `tools/intel/fetch-intel`.

The short version: **the highest CVSS in this Java batch is 7.5, not 9.x.** Nothing here is
in CISA KEV. It is a routine quarterly batch, and the interesting part is not the severity —
it is the gap between "affected" and "fixed" version numbers, which is where people get it
wrong (§2).

## 2. Affected vs. fixed — the part that bites

Oracle's risk matrix column is **"Supported Versions Affected."** Those are the versions you
are presumably running, *not* the versions you should be running. The fixes are separate
builds, all released **2026-10-20**:

| Line | Affected (Oracle's column, same list as IPA's 対象) | Fixed release | Fixed build | Release date |
|---|---|---|---|---|
| 8 | `8u503`, `8u503-perf` | **8u511** | `1.8.0_511-b09` | 2026-10-20 |
| 11 | `11.0.32.1` | **11.0.33** | `11.0.33+9` | 2026-10-20 |
| 17 | `17.0.20.1` | **17.0.21** | `17.0.21+9` | 2026-10-20 |
| 21 | `21.0.12.1` | **21.0.13** | `21.0.13+10` | 2026-10-20 |
| 25 | `25.0.4.1` | **25.0.5** | `25.0.5+9` | 2026-10-20 |
| 26 | `26.0.2` | — no `26.0.3` exists | — | superseded |
| 27 | `27` | **27.0.1** | `27.0.1+9` | 2026-10-20 |

Three consequences, each of which has bitten a real deployment:

1. **"I'm on 21.0.12.1, which is what Oracle listed" means you are on the affected build.**
   The fix is 21.0.13. The trailing `.1` is a patch-set update, not a fix for this CPU.
2. **JDK 26 gets no fix.** `26.0.3` does not exist (404 at Oracle), and the 26.0.2 release
   notes already say not to use it after the 2026-08-18 update. JDK 26 is a non-LTS line
   that hands over to 27; the only fix is to move lines.
3. **OpenJDK builds lag — but Temurin has now caught up on three of the five lines.** On
   2026-10-22 (12:07–17:28 UTC) Adoptium published `17.0.21+9`, `21.0.13+9` and `25.0.5+8`,
   matching Oracle's fixed versions by name. Its 8 and 11 lines are still the August builds
   (`8u504-b01`, `11.0.32.1+1`) — and those numbers **do not map onto Oracle's** `8u511` /
   `11.0.33`, so read the vendor's release notes rather than translating. Verified 2026-10-23
   via `api.adoptium.net`. If you run Corretto, Zulu or a distro package, the same rule holds:
   **your fix arrives on your vendor's schedule, and the version number will not look like
   Oracle's.**

   ```bash
   # Is my vendor's fixed build out yet? (JSON, no auth)
   curl -s 'https://api.adoptium.net/v3/assets/latest/21/hotspot?architecture=x64&image_type=jdk&os=linux' \
     | jq -r '.[0] | "\(.release_name)  \(.binary.updated_at)"'
   ```

## 4. Reading Notes 1/2/3 — client vs. server

Oracle marks every CVE with one of three applicability notes. The distinction decides whether
a headless server cares, and it is the single most misunderstood column:

| Note | Oracle's wording (summary) | Count here | Means for you |
|---|---|--:|---|
| **N1** | Applies to deployments running *untrusted code* in sandboxed applets / Java Web Start and relying on the sandbox. "Does not apply to Java deployments, typically in servers, that load and run only trusted code." | 12 | Desktop/browser trust boundary. On a headless server: usually out of scope. On a developer workstation or a JNLP user: in scope. |
| **N2** | Exploitable "by using APIs in the specified Component, e.g. through a web service which supplies data to the APIs"; also applies to sandboxed clients. | 31 | **Server-relevant.** Anything that parses untrusted input through JDK APIs (TLS, 2D/ImageIO, JAXP, JDBC, JGSS, Networking). |
| **N3** | Exploitable "only by supplying data to APIs in the specified Component without using untrusted Java Web Start applications or untrusted Java applets, such as through a web service." | 12 | Server-relevant, but assumes you expose that API to attacker-supplied data. |

Practical filter for a server estate: **N2 + N3 = 43 of 55** are worth assuming are yours until
proven otherwise. N1 matters for workstations, build agents, and anything running applets —
which in 2026 is essentially nothing, so treat N1 as "confirm, don't panic."

Oracle also states its scores assume the applet/JWS user has administrator privileges; without
them the impact ratings drop (its own example: 9.6 → 7.1). So a 7.5 here is not comparable to
a 7.5 in a network-service product.

## 5. Where Java actually hides

Java is rarely "the app". It is inside other things, which is why inventories miss it:

| Location | What to look for |
|---|---|
| Base images | `FROM eclipse-temurin:21`, `amazoncorretto:17`, `openjdk:8` — the tag freezes the patch level |
| App servers | Tomcat, Jetty, WildFly, WebLogic, WebSphere, GlassFish |
| Data layer | Elasticsearch / OpenSearch, Kafka, Zookeeper, Solr, Cassandra, Neo4j |
| CI & build | Jenkins (bundles a JRE), Gradle/Maven wrappers, Android SDK / `sdkmanager`, Sonar |
| Desktop & tooling | IDE-bundled JDKs, LibreOffice's JRE, DBeaver, Burp Suite, Neo4j Desktop |
| Vendored runtimes | Vendor appliances (network gear, CCTV, UPS, lab instruments) often ship an old JRE and never update it |
| Embedded | `jlink` images inside container images; `jpackage` bundles in installers |

Two rules that matter more than the list: **the tag is not the version** (a `21-jdk` image
built in March still says 21), and **`java -version` on the host is not the version your
container runs**.

## 6. Detection (read-only)

```bash
# What is actually running, per runtime, including build number
for j in $(command -v java javac 2>/dev/null) /usr/lib/jvm/*/bin/java; do
  [ -x "$j" ] && printf '%s -> ' "$j" && "$j" -version 2>&1 | head -1
done

# Every JVM the package manager knows about (Debian/Ubuntu, RHEL/Fedora, Arch)
dpkg -l 2>/dev/null | awk '/jre|jdk|openjdk|temurin/ {print $2, $3}'
rpm -qa 2>/dev/null | grep -Ei 'jdk|jre|java-.*openjdk'
pacman -Q 2>/dev/null | grep -Ei 'jdk|jre|java'

# Containers: the image tag lies, the binary does not
docker ps -q | xargs -r docker inspect --format '{{.Name}} {{.Config.Image}}'
docker ps -q | xargs -r -I{} sh -c 'docker exec {} java -version 2>&1 | head -1 | sed "s|^|{} |"'

# Vendor builds (read-only API calls)
curl -s 'https://api.adoptium.net/v3/assets/latest/21/hotspot?architecture=x64&image_type=jdk&os=linux' \
  | jq -r '.[0].release_name'
```

Compare the **build string** (`21.0.13+10`), not the marketing name. `21.0.12.1` and `21.0.13`
differ by one character and by every fix in §3.

## 7. Fixing it

| Your runtime | Action |
|---|---|
| Oracle JDK (licensed) | Install the 2026-10-20 CPU build for your line: 8u511 / 11.0.33 / 17.0.21 / 21.0.13 / 25.0.5 / 27.0.1 |
| JDK 26 | No fix exists. Move to 27.0.1 (JDK 26 is a non-LTS line past handover) |
| Temurin / Corretto / Zulu / Liberica | Wait for *that* vendor's build of the same upstream fixes; check their release notes, not Oracle's page |
| Distro packages | `apt install --only-upgrade openjdk-21-jre-headless` / `dnf upgrade java-21-openjdk` / `pacman -Syu jre-openjdk` |
| Container images | Rebuild on the vendor's fixed tag and redeploy; do not `docker cp` a JRE into a running container |
| CI runners / build agents | Update the JDK the toolchain uses, then rebuild artifacts — a rebuilt jar on an old JRE is still exposed |

Verify afterwards with the §6 commands on the *running* process, and check both host and
container. Then re-check the JVM's own view:

```bash
java -XshowSettings:properties -version 2>&1 | grep -E 'java.version|java.vendor'
```

## 8. Things not to do

- **Don't treat Oracle's "Supported Versions Affected" as the fix list.** 21.0.12.1 is affected;
  21.0.13 is fixed. This is the most common error with Oracle Java advisories.
- **Don't compare version numbers across vendors.** Temurin's `8u504` and Oracle's `8u503` are
  different numbering schemes for the same upstream line; neither is "newer" in a way that
  answers "am I fixed?"
- **Don't call a JRE update done because the image tag changed.** Tags are rebuilt in place;
  read `java -version` from the running container.
- **Don't skip N1 CVEs on shared developer machines.** Sandbox escapes need a sandbox; build
  agents and IDEs are where untrusted code runs.
- **Don't report "no Java" without checking.** It is in Elasticsearch, Jenkins, and vendor
  appliances more often than in `dpkg -l | grep java`.
