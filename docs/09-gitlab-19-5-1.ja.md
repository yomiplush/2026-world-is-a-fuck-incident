# GitLab 19.5.1 — CVE-2026-110264、CVSS 10.0 の未認証 RCE

[English](09-gitlab-19-5-1.md) | [**日本語**](09-gitlab-19-5-1.ja.md)

このバッチで最高スコアにして最大の影響範囲。GitLab の正規表現コンパイラにおける **10.0** の
整数オーバーフローで、**未認証**の利用者が self-managed サーバ上でコードを実行できます。
**12年分（2014年の 7.0 以降）のリリース**が該当します。

以下の事実は GitLab 公式のパッチリリースページ
[`docs.gitlab.com/releases/patches/patch-release-gitlab-19-5-1-released/`](https://docs.gitlab.com/releases/patches/patch-release-gitlab-19-5-1-released/)
を `tools/intel/fetch-intel --sources gitlab` で
[`data/2026-10-22/gitlab-patch-release-gitlab-19-5-1-released.json`](../data/2026-10-22/gitlab-patch-release-gitlab-19-5-1-released.json)
に構造化したものです。

## 1. 何が起きたか

| 項目 | 値 |
|---|---|
| CVE | **CVE-2026-110264** |
| 名称 | Integer Overflow issue in Regular Expression Compiler |
| 深刻度 | **Critical**、CVSS **10.0**（`CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H`） |
| 結果 | 未認証の利用者が GitLab サーバ上で任意コードを実行できる |
| 原因 | 細工した正規表現をコンパイルする際の整数オーバーフロー |
| 報告者 | `joaxcar`（GitLab の HackerOne プログラム経由） |
| 修正 | 2026-10-21、7ブランチ同時 |
| 悪用 | GitLab は悪用を報告していない。2026-10-22 時点で **CISA KEV には未収載** |

`PR:N`（認証不要）で `S:C`（影響がコンポーネントの外に及ぶ）の 10.0 です。「認証は必要だが
低権限」のような逃げ道がなく、**Web インターフェースに到達できること自体**が前提条件です。

## 2. 影響版と修正版

GitLab の表記は「**7.0 以降の全版**のうち、以下より前」＋各ブランチです。

| 使っている版 | 上げる先 |
|---|---|
| 19.5.x（19.5.1 未満） | **19.5.1** |
| 19.4.x（19.4.3 未満） | **19.4.3** |
| 19.3.x（19.3.6 未満） | **19.3.6** |
| 19.2.x（19.2.9 未満） | **19.2.9** |
| 19.1.x（19.1.9 未満） | **19.1.9** |
| 19.0.x（19.0.10 未満） | **19.0.10** |
| 7.0 〜 18.11.12 | **18.11.13** |

このうち4つ（18.11.13 / 19.0.10 / 19.1.9 / 19.2.9）は **GitLab の通常サポート範囲の外**です。
方針上は「現行＋過去2か月」のみ。GitLab は「重大な問題に限って行う措置」として、通常リリースの
上にバックポートしたと述べています。**19.0 / 19.1 / 19.2 を使っていて「対象外」と考えていた
なら、対象です。**

### 罠: 9日前にパッチを当てていても足りない

1つ前のパッチリリース（2026-10-12）は 19.2 以降しか対象にしておらず、今回の修正版は
**その1つ上**です。10月12日に最新化した環境は、今日また該当します。

> **見るべきは版であって、保守の履歴ではない。**「先週パッチを当てた」が、この CVE が
> 捕まえる状態そのものです。

## 3. なぜ 7.0（2014年）まで遡るのか

GitLab は Ruby 標準の正規表現エンジン **Onigmo** を自前のパッケージに同梱し、自前のビルドで
パッチを当てています。したがってエンジン側の弱点は、それを同梱した全リリース、つまり 7.0
以降のすべてに存在します。「誰かが更新を忘れた古い版」ではなく、**各パッケージに同じコードが
コンパイルされている**という話です。

GitLab は、攻撃者が脆弱なコンパイラに到達するための**前提条件を公開していません**。これは
2つの判断に効きます。

- 「自分の構成ではその経路を露出していない」と**確実には言えない**。
- 正確な WAF ルールはまだ作れない。代わりに GitLab は検知ルールを2つ公開しました。

## 4. GitLab が公開した検知

いずれも GitLab 自身のアプリケーションログに対する Sigma ルールで、オープンソースの
**TLDR** フレームワークの一部として公開されています（[docs](https://docs.gitlab.com/security/detecting_security_incidents/)）。

| 検知 | 何を見るか |
|---|---|
| **Onigmo native worker crash** | 整数オーバーフローの試行が失敗したときに worker に残るクラッシュ痕跡 |
| **Org mode render error burst** | 描画エラーのバースト（観測できる第2の経路） |

これは**試行**を捕まえるもので、成功は捕まえません。ヒットしたら「誰かが試した」と解釈し、
その後に何が起きたか（管理者の追加、ランナーの追加、CI 変数の変更、外向き通信）を確認します。

## 5. やること

### 5-1. 何を動かしているか確認する（読み取りのみ）

```bash
# Omnibus
sudo gitlab-rake gitlab:env:info 2>/dev/null | head -20
cat /opt/gitlab/version-manifest.txt 2>/dev/null | head -1

# コンテナ
docker ps --filter name=gitlab -q | xargs -r -I{} \
  sh -c 'docker exec {} cat /opt/gitlab/version-manifest.txt 2>/dev/null | head -1'

# パッケージ
dpkg -l 2>/dev/null | awk '/gitlab/ {print $2, $3}'
rpm -qa 2>/dev/null | grep -i gitlab

# API（トークンが必要。無ければ省略）
curl -s --header "PRIVATE-TOKEN: <token>" https://gitlab.example.com/api/v4/version
```

### 5-2. アップグレード

```bash
# Omnibus（Debian/Ubuntu のリポジトリ導入）
sudo apt update && sudo apt install --only-upgrade gitlab-ee   # CE なら gitlab-ce
sudo gitlab-ctl reconfigure

# コンテナ: タグを動かす。起動中のコンテナを書き換えない
docker pull gitlab/gitlab-ee:19.5.1-ee.0
```

GitLab のアップグレード経路の制約はいつもどおり有効です（PostgreSQL / Rails のマイグレーションを
任意に飛ばせない）。18.x 以前から上げる場合は、開始前に目標版の経路を確認してください。
**障害対応中の失敗したアップグレードは、計画的な1回より高くつきます。**

### 5-3. 今日上げられない場合

公開された回避策はありません。正直に言える緩和は「露出を減らす」だけです。

- インスタンスを ACL / VPN / IP 許可リストの内側に置き、未認証のインターネットから届かない
  ようにする（`AV:N` の経路を消す＝リスクの本体を消す）。
- 利用者が正規表現を投入できる機能（リポジトリのファイルフィルタ、CI の正規表現、連携機能）を、
  トリガーが判明するまで無効化・制限する。
- 上記の検知2つを有効にし、worker のクラッシュを監視する。

**これを「修正」と呼ばないこと。** 時間を買うだけで、バグは消えていません。

### 5-4. 上げたあと

- 未修正のまま露出していた可能性があるなら、到達可能だった資格情報をローテートする:
  ランナートークン、CI/CD 変数、デプロイキー、レジストリ資格情報、`gitlab.rb` の secrets。
- 自分が作っていない管理者ユーザー、個人アクセストークン、ランナーが無いか確認する。
- GitLab.com と GitLab Dedicated の利用者は対応不要（Dedicated は 19.3.5-internal0 /
  19.4.2-internal0 以降で修正済み）。**対象は self-managed のみ**——だから見落としやすく、
  見落とすと高くつきます。

## 6. 同じリリースの残り（12件）

10.0 を直すついでに11件が直ります。うち2件は小さくありません。

| CVE | 深刻度 | 内容 |
|---|---|---|
| CVE-2026-15723 | High, 8.2 | OmniAuth→LDAP の自動リンク: 認証済み利用者が、対象者の操作なしに既存 LDAP アカウントを乗っ取れる |
| CVE-2026-112212 | High, 7.5 | OAuth/OIDC discovery のキャッシュ汚染で、フローを攻撃者のサーバへ誘導できる |
| CVE-2026-12664 | 6.8 | GraphQL の項目で `read_api` トークンがプロジェクトの受信メールアドレスを読める |
| その他 | 2.7 〜 5.9 | アクセス制御、ヘッダ経由の資格情報露出、AI Gateway ヘッダ、キャッシュ漏えい、承認ポリシーの迂回 |

ベクター込みの全件は JSON にあります。2件目に注意: GitLab を OIDC プロバイダとして使って
いるなら、修正済みでも discovery ドキュメントが利用者間でキャッシュされていないか確認する
価値があります。
