# GitLab 19.5.1 — CVE-2026-110264, CVSS 10.0 unauthenticated RCE

[English](09-gitlab-19-5-1.md) | [**日本語**](09-gitlab-19-5-1.ja.md)

The highest-scoring item in this batch, and the one with the largest blast radius: a **10.0**
integer overflow in GitLab's regular-expression compiler that an **unauthenticated** user can
use to run code on a self-managed server. Twelve years of releases are affected.

Facts below come from GitLab's own patch-release page,
[`docs.gitlab.com/releases/patches/patch-release-gitlab-19-5-1-released/`](https://docs.gitlab.com/releases/patches/patch-release-gitlab-19-5-1-released/),
parsed into [`data/2026-10-22/gitlab-patch-release-gitlab-19-5-1-released.json`](../data/2026-10-22/gitlab-patch-release-gitlab-19-5-1-released.json)
by `tools/intel/fetch-intel --sources gitlab`.

## 1. What it is

| Field | Value |
|---|---|
| CVE | **CVE-2026-110264** |
| Title | Integer Overflow issue in Regular Expression Compiler |
| Severity | **Critical**, CVSS **10.0** (`CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H`) |
| Result | unauthenticated user can execute arbitrary code on the GitLab server |
| Cause | integer overflow when compiling a specially crafted regular expression |
| Reported by | `joaxcar` via GitLab's HackerOne program |
| Fixed | 2026-10-21, seven branches at once |
| Exploited? | No exploitation reported by GitLab; **not in CISA KEV** as of 2026-10-22 |

A 10.0 vector with `PR:N` and `S:C` means: no credentials, no user interaction, and the
compromise escapes the vulnerable component's scope. There is no "authenticated but low
privilege" qualifier to hide behind — reachability of the web interface is the whole
precondition.

## 2. Affected and fixed

GitLab lists impacted ranges per branch. All of them are "**all versions from 7.0** before
18.11.13" plus each newer branch:

| You run | Upgrade to |
|---|---|
| 19.5.x before 19.5.1 | **19.5.1** |
| 19.4.x before 19.4.3 | **19.4.3** |
| 19.3.x before 19.3.6 | **19.3.6** |
| 19.2.x before 19.2.9 | **19.2.9** |
| 19.1.x before 19.1.9 | **19.1.9** |
| 19.0.x before 19.0.10 | **19.0.10** |
| 7.0 – 18.11.12 | **18.11.13** |

Four of those (18.11.13, 19.0.10, 19.1.9, 19.2.9) are **outside GitLab's normal support
window** — the policy covers the current release plus the two previous monthly ones. GitLab
says it backported on top of the standard releases, "a step it reserves for severe issues".
Treat that as the signal it is: if you are running 19.0, 19.1 or 19.2 and thought you were
out of scope, you are not.

### The trap: patching nine days earlier is not enough

The previous patch release (2026-10-12) only covered 19.2 and later, and this fix sits **one
patch above it**. An instance that was fully up to date on 12 October is affected again today.

> **Check the version, not the maintenance history.** "We patched last week" is exactly the
> state this CVE catches.

## 3. Why it reaches back to 7.0 (2014)

GitLab ships Ruby's built-in regular-expression engine, **Onigmo**, inside its own packages and
patches it in its own builds. A weakness in that engine therefore exists in every release that
shipped it — which is every release since 7.0. This is not "an old version someone forgot to
update"; it is the same code compiled into each package.

GitLab has **not published the preconditions** an attacker needs to reach the vulnerable
compiler. That matters for two decisions:

- You cannot reliably argue "my deployment does not expose that path".
- You cannot build a precise WAF rule yet. GitLab instead published two detections.

## 4. Detections GitLab shipped

Both are Sigma rules written against GitLab's own application logs, released as part of
GitLab's open-source **TLDR** framework
([docs](https://docs.gitlab.com/security/detecting_security_incidents/)):

| Detection | What it looks for |
|---|---|
| **Onigmo native worker crash** | the crash signature a failed integer-overflow attempt leaves in the workers |
| **Org mode render error burst** | a burst of render errors, the second observable path |

These catch **attempts**, not success. Treat a hit as "someone tried", then look for what
followed (new admin users, new runners, changed CI variables, outbound connections).

## 5. What to do

### 5-1. Find out what you run (read-only)

```bash
# Omnibus
sudo gitlab-rake gitlab:env:info 2>/dev/null | head -20
cat /opt/gitlab/version-manifest.txt 2>/dev/null | head -1

# Container
docker ps --filter name=gitlab -q | xargs -r -I{} \
  sh -c 'docker exec {} cat /opt/gitlab/version-manifest.txt 2>/dev/null | head -1'

# Package
dpkg -l 2>/dev/null | awk '/gitlab/ {print $2, $3}'
rpm -qa 2>/dev/null | grep -i gitlab

# API (needs a token; omit if you have none)
curl -s --header "PRIVATE-TOKEN: <token>" https://gitlab.example.com/api/v4/version
```

### 5-2. Upgrade

```bash
# Omnibus, Debian/Ubuntu repository install
sudo apt update && sudo apt install --only-upgrade gitlab-ee   # or gitlab-ce
sudo gitlab-ctl reconfigure

# Container: move the tag, do not mutate the running container
docker pull gitlab/gitlab-ee:19.5.1-ee.0
```

GitLab's own upgrade path rules still apply (you cannot skip postgres/rails migrations
arbitrarily). If you are on 18.x or older, read the upgrade-path doc for your target version
before starting — a failed upgrade during an emergency is worse than a planned one.

### 5-3. If you cannot upgrade today

There is no published workaround, so the only honest mitigations are scope reductions:

- Put the instance behind an ACL / VPN / IP allowlist so unauthenticated internet clients
  cannot reach it (this removes the `AV:N` path, which is the whole risk).
- Disable or restrict features that let users supply regular expressions (repository file
  filters, custom CI regex, integrations) until you know the trigger.
- Turn on the two detections above and watch for worker crashes.

**Do not describe any of that as a fix.** It buys time; it does not remove the bug.

### 5-4. After upgrading

- Rotate anything the instance could reach if it was exposed while unpatched: runner tokens,
  CI/CD variables, deploy keys, registry credentials, the `gitlab.rb` secrets bundle.
- Check for admin users, personal access tokens, and runners you did not create.
- GitLab.com and GitLab Dedicated customers need no action (Dedicated is fixed at
  19.3.5-internal0 / 19.4.2-internal0 and later). **Only self-managed installs are in scope** —
  which is the reason this is easy to dismiss and expensive to get wrong.

## 6. The rest of the release (12 CVEs)

Patching for the 10.0 also fixes 11 others, two of which are not trivial:

| CVE | Severity | Issue |
|---|---|---|
| CVE-2026-15723 | High, 8.2 | OmniAuth→LDAP auto-linking: an authenticated user can take over an existing LDAP-backed account without the target's interaction |
| CVE-2026-112212 | High, 7.5 | Cache poisoning of OAuth/OIDC discovery endpoints can redirect flows to an attacker-controlled server |
| CVE-2026-12664 | 6.8 | GraphQL work-item field lets a `read_api` token read a project's incoming email address and create work items |
| others | 2.7 – 5.9 | access control, credential exposure in headers, AI Gateway header, cache leak, approval-policy bypass |

The full set with vectors is in the JSON. Note the second one: if you run GitLab as an OIDC
provider, that CVE is worth its own look even on a patched instance (check your discovery
documents are not being cached across users).
