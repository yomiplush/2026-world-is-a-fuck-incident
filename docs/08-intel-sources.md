# Where the incident data comes from — sources, snapshot, and an AI handoff

[English](08-intel-sources.md) | [**日本語**](08-intel-sources.ja.md)

A CVE list is stale the moment it is written. What stays useful is the **set of sources** and
the exact way to re-ask them. This document is that set: 12 researcher/industry feeds, four
official feeds, one collector, and the snapshot they produced on **2026-10-22**.

Everything in §3 is generated by `tools/intel/fetch-intel` into
[`data/2026-10-22/`](../data/2026-10-22/). Nothing here is hand-copied, because a hand-copied
count is a claim you cannot re-check.

## 1. Four questions, in the order they matter

Chasing everything published in a week is how the one item that matters gets missed. Ask in
this order, and stop as soon as the answer is "not mine":

| # | Question | Source that answers it | If "no" |
|---|---|---|---|
| 1 | Do I run it? | your inventory — not a feed | stop |
| 2 | Is the claim from the party that owns it? | vendor advisory / CNA record | downgrade to "unconfirmed" |
| 3 | Is it being exploited *in the wild*? | CISA KEV | treat as "no known exploitation", not "safe" |
| 4 | Does it reach my exposed surface? | vendor advisory + your topology | schedule, don't page |

Feed order follows the same logic: the finding's authors first (they know the limits of their
own claim), then vendor incident response, then official catalogs, then policy research.

Notes that change how you read them:

- **KEV is a claim of exploitation, not of severity.** Absence means "not confirmed", and it
  lags disclosure. It is also US-scoped: a CVE exploited only in Japan may never appear.
- **NVD is often `Awaiting Analysis` for Oracle/Microsoft records.** For those, the vendor
  matrix is the primary source and NVD is a mirror that arrives later.
- **MSRC counts entries, not vulnerabilities.** One CVE appears once per affected product
  build. "2,575 entries" is not "2,575 bugs".
- **JVN ≠ JVN iPedia.** `jvn.jp` advisories are up; the `jvndb` search API was returning a
  maintenance page at collection time (§5).
- **The lead channel is not a source.** A post or a headline tells you *where to look*; the link
  it carries is what you cite. Both are collected with their URLs for exactly that reason
  (`x-posts.json`, `news-feeds.json`), and `docs/22` §4 is the worked example: four incidents
  named first by the news channel, each then checked against the vendor's own page.
- **A filter is a source too.** The CRITICAL sweep selects on CVSS 3.x severity, and it counts
  only NVD's own score: `?cveId=CVE-2026-91637&cvssV3Severity=CRITICAL` returns **0 rows** while
  the record holds a CNA 9.9, and the same is true of `CVE-2026-111497` (CVSS 4.0 only, 9.2) and
  `CVE-2026-114625` (CNA 9.9). A CNA-scored critical never appears in that list. Read the unfiltered published sweep when the question is "what is exploited",
  and the filtered one only when the question is "what scored highly".

## 4. "Exploited" means four different things

The same week produced four mutually compatible statements about php2shell, and reading them
as contradictory is a common and costly mistake:

| Statement | Source | What it actually claims |
|---|---|---|
| "CISA has **not observed exploitation** … as of the time of publication" | CISA alert, 2026-10-21 | no confirmed in-the-wild incidents **in CISA's visibility**, and it is not in KEV |
| "Unit 42 has seen **proof of concept**" | Unit 42 threat brief, 2026-10-21 | a working exploit exists publicly or semi-publicly |
| "At least one European government took its website **offline as a precaution**" | Unit 42, 2026-10-21 | someone judged the risk high enough to act, with no incident confirmed |
| Attack **attempts observed before** the fixed release shipped (2026-10-21 07:43 UTC) | this repo, `docs/00` (Cloudflare) | someone was already sending traffic that looks like the exploit; that is not the same as a successful compromise |

Conclusion an AI (or a human) should draw: **"no KEV entry" + "public PoC" is a normal
combination** and it means "exposed, not yet burning". It justifies patching today; it does not
justify a breach investigation.

## 5. Failure modes to expect (observed, not hypothetical)

| Failure | What it looked like on 2026-10-22 | What to do instead |
|---|---|---|
| **JVN iPedia / MyJVN API down** | `https://jvndb.jvn.jp/myjvn?...` returned an HTML page titled メンテナンス中 ("under maintenance") instead of XML, for every query shape tried | use the `jvn.jp` advisory feed (works), and IPA's own alert pages; do not silently substitute NVD for Japanese vendor coverage |
| **MSRC blog `/feed` is not a feed** | `msrc.microsoft.com/blog/feed` returned `text/html`, 200, with zero items | use `microsoft.com/security/blog/feed/` (works) or the CVRF API |
| **A "count" moved between reads** | `docs/05` recorded 2,578 MSRC entries; the same CVRF re-issued 2026-10-21 yields 2,575 | re-derive counts, never copy them; cite the retrieval time |
| **NVD has no analysis yet** | Oracle's Oct CVEs are `Awaiting Analysis` | read the vendor risk matrix for CVSS and affected versions |
| **Vendor build lag** | Temurin's newest builds were still the August ones two days after Oracle's CPU | check the vendor's release notes before telling anyone to upgrade |

None of these is exotic. Three of the five are just "the source was not the shape I assumed",
which is exactly what an agent with a shell can check in one command and a human usually does
not.

## 6. Handing this to an AI

The point of the prompt is not to give the model facts — the files do that. It is to stop the
model from **inventing the parts the files do not cover**. Copy
[`prompts/intel-prompt.txt`](../prompts/intel-prompt.txt) (Japanese:
`intel-prompt.ja.txt`) and paste it with the repository URL and your environment block.

```bash
bash tools/copy-prompt.sh intel        # English
bash tools/copy-prompt.sh intel ja     # Japanese
```

The prompt enforces five things, in this order:

1. Read `docs/07`, `docs/08`, `SOURCES.md` before answering. Do not add CVEs from memory.
2. Re-run `tools/intel/fetch-intel` first, and **say if the numbers moved** — an answer built on
   a stale snapshot must announce itself as stale.
3. Separate *affected* from *fixed* version numbers, and never report a vendor's "affected"
   list as the fix list (the Oracle trap in `docs/07` §2).
4. Quote the source for each claim, with its retrieval date, and mark anything from a single
   secondary source as unconfirmed.
5. Output the four lists: confirmed in my environment / needs action / cannot determine /
   ruled out — plus what would change the answer.

What to paste alongside: your OS/patch tooling, whether the host is internet-facing, which
runtimes you know about, and the raw output of the §6 detection commands. An agent that has the
version strings spends its budget on judgement instead of guessing.

## 7. Re-fetching

```bash
tools/intel/fetch-intel --date 2026-10-22 --cpu Oct2026 --month 2026-Oct
tools/intel/fetch-intel --sources oracle,kev        # subset
tools/intel/fetch-intel --out /tmp/intel --limit 20 # somewhere else, more items per feed
```

Exit codes: `0` all sources fetched, `10` partial (the rest was written), `2` nothing fetched.
Python 3 standard library and network access only — no jq, no bs4. Identical command, identical
file names, so `git diff` between two snapshots shows exactly what the world changed, and
`--date` keeps history instead of overwriting it.
