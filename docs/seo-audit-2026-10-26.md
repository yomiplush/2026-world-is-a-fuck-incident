## Crawling, static HTML and languages

Google can execute JavaScript, but content requiring button presses is a separate problem: Google documents that crawlers do not click buttons to reveal additional content. A `noscript` archive link does not supply the missing briefing text when JavaScript is available but no unlock occurs. [Google: incremental loading](https://developers.google.com/search/docs/specialty/ecommerce/pagination-and-incremental-page-loading), [Google: JavaScript SEO](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics).

A bounded fix is a visible initial-HTML editorial summary linking to `/timeline`, the latest review and the 12 static Tailworm versions. Existing full daily/report pages can remain the primary article destinations; every animation scene does not need a separate indexed URL. Treat `#41` and other scene fragments as playback state, not independent article URLs. Google recommends ordinary `a[href]` URLs and warns against fragment-based content routing. [Google: JavaScript SEO](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics).

For Tailworm, retain reciprocal, fully qualified `hreflang` links including each page itself, matching the URLs actually returned as final `200` pages. Keep each translated article's self-canonical; do not canonicalize all translations to Japanese. `zh-Hans` is appropriate to Simplified Chinese. `x-default` should point to the chosen language-neutral entry or documented default. [Google: localized versions](https://developers.google.com/search/docs/specialty/international/localized-versions).

**Japanese routing needs deliberate handling:** `tailworm-language.js` redirects the Japanese default according to saved/browser language when no query exists. Current `?lang=ja` forces stable Japanese content. Merely removing that query from the canonical while preserving this behavior could make the Japanese canonical render English for an English-language crawler. Either retain `/tailworm?lang=ja` as the Japanese canonical initially, or make `/tailworm` consistently Japanese and leave language changes to explicit user controls. Explicit translated paths already take precedence over browser preference. This is an implementation inference from the current script, not a Google indexing observation.

## Truthful structured data and metadata

1. Add `WebSite` JSON-LD on the canonical homepage with the actual publication name and new-origin URL. Use the same visible site name consistently. A site name declaration helps describe the publication; it does not promise Google's displayed result. [Google: site names](https://developers.google.com/search/docs/appearance/site-names).
2. Individual substantive reviews and Tailworm articles can use `Article`, with matching visible headline, language, canonical `mainEntityOfPage` and real author attribution. Add publication/modified timestamps only when supported by publishing records. Include an image only if it genuinely represents that article. `NewsArticle` is an editorial choice only for pages actually presented as news articles, not a reason to reclassify the whole archive. [Google: Article](https://developers.google.com/search/docs/appearance/structured-data/article).
3. The timeline is a collection of reports; `CollectionPage`/`ItemList` may describe its visible list, without claiming a guaranteed Google rich-result feature. Add breadcrumb markup only alongside an actual, visible hierarchy. Structured data must represent the page users can read. [Google: structured-data policies](https://developers.google.com/search/docs/appearance/structured-data/sd-policies).
4. Keep incident date, research cutoff, retrieval time and page publication/update time distinct. For example, the Tailworm research cutoff is not automatically the date the article was first published. Visible byline dates should say what they mean and agree with structured dates. [Google: publication dates](https://developers.google.com/search/docs/appearance/publication-dates).
5. Set unique page titles/descriptions, appropriate social locale and new-origin image URLs. Do not invent an organization, named credentials, ratings or publication timestamps. Validate JSON-LD with Google's Rich Results Test after deployment; valid markup does not ensure a rich result. [Google: structured-data policies](https://developers.google.com/search/docs/appearance/structured-data/sd-policies).

## Migration and Search Console plan

1. **Prepare the new origin.** Regenerate metadata, static entry content, language links, sitemap and real 404 behavior. Verify final `200` URLs before enabling host redirects. Keep the content/path structure stable where possible; clean-URL normalization should follow the hosting behavior already in production.
2. **Consolidate hosts.** Redirect each old custom-host URL to its equivalent new `www` URL, preserving path and useful query parameters. Configure apex→`www` in the new zone and legacy Pages hostname→custom domain. Avoid redirecting every old article to the homepage or introducing self-loops. Use Cloudflare's path/query-preserving redirect patterns; redirects need proxied DNS for zone redirect rules. [Cloudflare: apex to WWW](https://developers.cloudflare.com/rules/url-forwarding/examples/redirect-root-to-www/), [Cloudflare: Pages custom-domain redirect](https://developers.cloudflare.com/pages/how-to/redirect-to-custom-domain/), [Cloudflare: redirect rules](https://developers.cloudflare.com/rules/url-forwarding/).
3. **Publish and submit the sitemap.** Include canonical, indexable final `200` destinations, not `.html` redirect aliases, playback fragments or unsupported locale shells. Set `lastmod` from significant page changes; omit it when unknown. Google ignores `priority` and `changefreq`, so tuning those is not useful. Submission is a discovery hint, not an indexing guarantee. [Google: sitemap guidance](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap).
4. **Use the already registered Search Console domain.** User reports registration of the new domain. Check its actual verified property and add a `https://www.infosec-briefing.net/` URL-prefix view if useful; a Domain property covers protocols and subdomains. Confirm both old and new ownership before using Change of Address. [Search Console: property types](https://support.google.com/webmasters/answer/34592?hl=en).
5. **Request the move after redirects work.** Use Change of Address from the old site property only after prechecks pass. The tool requires ownership of old and new properties under the same account. Registration alone does not perform the migration. [Search Console: Change of Address](https://support.google.com/webmasters/answer/9370220?hl=en).
6. **Monitor and retain redirects.** Inspect representative root, daily report, latest review and translated Tailworm URLs; monitor Google-selected canonical, indexing exclusions and crawl errors. Keep permanent redirects for at least a year, preferably longer for existing bookmarks. Temporary indexing/ranking fluctuations are possible while Google processes the move. [Google: site moves](https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes).
