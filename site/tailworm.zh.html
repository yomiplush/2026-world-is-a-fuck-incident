SSH / 发现 1–3、5

Tailscale SSH

前提是获准连接已启用 SSH 的节点，并拥有相关转发权限。报告称，root 对 Unix socket 的操作及路径竞争可能造成权限越界。

检查：已启用节点、SSH 规则、不必要的转发
自托管 / 发现 6

headscale

报告指出，0.29.5 的公开注册路径可能导致内存耗尽和缓存驱逐。研究者还指出无法阻止 SSH 转发。

检查：公开范围、SSH 授权、内存与注册监控
实验性 / 发现 4

conn25 连接器

研究指出，拥有 conn25 使用 capability 的设备可选择连接器的实际目标。请检查通往 LAN、metadata 和 cluster 的路径。

检查：是否使用 conn25、使用权限、实际目标的出口流量

02 / 今天采取行动

核查并缩小授权范围。

  1. 盘点 SSH 的实际可达范围。将访问限制为必要用户与设备到必要目标，减少不必要的转发。区分普通 OpenSSH 连接与 Tailscale SSH。
  2. 对关键主机，也可考虑暂时停用 SSH。先确认替代管理路径，再作决定。不能认为仅指定非 root 用户就足以防止本次权限提升。这并非厂商要求所有人一律停用的建议。
  3. 不要将 check mode 称为修复。入口处的额外认证有用，但无法消除已获准会话内部的权限问题。
  4. 分别审视 headscale、连接器和 Serve。检查公开注册路径、内存限制、不必要的 conn25 权限和特权 socket 转发。IP firewall 无法阻止本地 socket 竞争。Kubernetes 的出口限制也应在实际路径上验证。
  5. 对照官方公告安排更新。在支持自动更新的环境中启用该功能，并跟踪修复版本通知。分别管理受影响版本、修复版本与配置缓解措施。

只读检查的起点。请勿公开结果或配置中包含的秘密信息。

tailscale version
tailscale serve status
tailscale funnel status

03 / 怀疑遭到入侵时

重建系统，撤销设备身份。

隔离设备并保全证据，通过控制平面删除或撤销设备，并轮换已暴露的注册密钥和 API 凭据。如果 root 权限被攻陷，还应调查 state 是否可能被复制。仅重新安装操作系统无法撤销已被带走的密钥。如果签名节点受影响，还需考虑 Tailnet Lock 密钥。
