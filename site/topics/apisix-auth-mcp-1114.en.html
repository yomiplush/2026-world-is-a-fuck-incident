Apache APISIX: 7 flaws across identity headers, path normalization and openapi-to-mcp boundaries

7 vulnerabilities fixed in Apache APISIX 3.20.0: client-supplied identity headers survive when multi-auth falls back from wolf-rbac (CVE-2026-124666, 3.8.0–3.19.0) or when jwe-decrypt uses `strict: false` or forward-auth uses `allow_degradation: true` (CVE-2026-124679, 3.18.0–3.19.0); encoded dot-segment mismatches bypass route-level auth on shared upstreams (CVE-2026-124680, 0.9–3.19.0); authz-keycloak grants access when holding any single required scope including denied HTTP methods (CVE-2026-124716, 1.4.0–3.19.0); combining `match_uri_encoded_slash` and `skip_mtls_uri_regex` bypasses mTLS on paths decoding to exempted URIs (CVE-2026-124723, 3.18.0–3.19.0); and openapi-to-mcp allows caller identity spoofing and relative path traversal to undeclared API endpoints (CVE-2026-124719 and CVE-2026-124726, 3.19.0).

What to check

Upgrade Apache APISIX to 3.20.0. Audit route plugin configurations (`strict: false`, `allow_degradation: true`, `match_uri_encoded_slash`, and `openapi-to-mcp`) and verify whether upstream services blindly trust caller-supplied identity headers.

A first fixed version is listed only when the advisory provides one. Advisory counts are not incident counts.
