L143: 
L144: <= 3.4.16

L146: ## Patched versions
L147: 
L148: 3.4.17
L149: 
L150: ## Description
L151: ### Summary
L152: 
L153: DOMPurify drops `attributeName` attributes whose value contains `href`, so an allowed `<animate>` or `<set>` can't rewrite a link's href after sanitizing. The check compares the attribute name after `transformCaseFunc`, and that function doesn't lowercase in XHTML mode. In XHTML the attribute is spelled `attributeName`, so the comparison with `"attributename"` never matches and the guard does nothing.
L154: An app that uses `PARSER_MEDIA_TYPE: 'application/xhtml+xml'` and allows `animate` and `attributeName` will keep `<animate attributeName="href" values="x;javascript:alert(1)">`. Clicking the parent link then runs the script.
L155: 
L156: This needs a non-default config, so going by SECURITY.md I'd file it as a hardening bug rather than a bypass of the default config.
L157: ### Details
L158: 
L159: In `_sanitizeAttributes` (dist/purify.js line 2216 in 3.4.16):
L160: 
L161:     const lcName = transformCaseFunc(name);
L162:     ...
L163:     if (lcName === "attributename" && stringMatch(value, "href")) {
L164:       _removeAttribute(name, currentNode, attr);
L165:       continue;
L166:     }

L147: ## Description
L148: ### Summary
L149: 
L150: The 3.4.16 fix for 【71†GHSA-p98j-92pf-mc4p】 only covers a hook that removes the node it was called for. If an `IN_PLACE` hook removes a different node, like the current node's parent or a sibling that has not been visited yet, that subtree is never walked or neutralized. Event handlers in it stay on the elements, and an `<img onerror>` that was already loading fires after `sanitize()` returns.
L151: The README says: "Nodes that a hook detaches from the tree ... are treated as removed. In IN_PLACE mode their subtree is neutralized inline, so an `<img onload>` that was already loading when you built the live tree cannot fire after `sanitize()` returns." That does not hold when the detached node is not the hook's own node.
L152: ### Tested versions
L153: 
L154:   * 3.4.16 (latest) and main at 【72†`18f8f0e`】
L155:   * also 3.4.15, 3.4.12 and 2.5.8

L157: jsdom for the matrix below, and Chromium (Playwright) for the event actually firing.

L161: 
L162:     if (currentNode === root || getParentNode(currentNode) !== null) {

L130: # SAFE_FOR_TEMPLATES bypass: split template expressions survive in attached shadow root content on DOM output modes
L131: 
L132: Low
L133: 
L134: 【61†cure53】 published GHSA-cg2g-xh64-v4q7 Oct 12, 2026
L135: 
L136: ## Package
L137: 
L138: dompurify (【70†npm】)
L139: 
L140: ## Affected versions
L141: 
L142: >= 3.4.4, <= 3.4.16
L143: 
L144: ## Patched versions
L145: 
L146: 3.4.17
L147: 
L148: ## Description
L149: ## Summary
L150: When DOMPurify is configured with `SAFE_FOR_TEMPLATES: true` together with a DOM-returning mode (`RETURN_DOM: true`, `RETURN_DOM_FRAGMENT: true`, or `IN_PLACE: true`), template expressions such as `{{...}}`, `${...}`, and `<%...%>` survive sanitization inside the text content of an attached shadow root. The post-walk safety net `_scrubTemplateExpressions` (`src/purify.ts:1717`) was extended to recurse into `<template>.content`, but it never recurses into attached shadow roots.
L151: An attacker who can supply a DOM node carrying a shadow root (the `IN_PLACE` and shadow-aware `RETURN_DOM` surfaces) can split an expression across text nodes separated by disallowed elements; after those elements are removed the fragments become adjacent and serialize into a complete expression that a downstream template engine will evaluate.
L152: ## Root Cause
L153: `SAFE_FOR_TEMPLATES` neutralizes template expressions through two mechanisms: a per-text-node strip during the main walk (`_stripTemplateExpressions`, applied in `_sanitizeElements` at `src/purify.ts:2246`), and a final post-walk pass (`_scrubTemplateExpressions`, `src/purify.ts:1717`) that normalizes adjacent text nodes and re-strips expressions that only form after merging.
